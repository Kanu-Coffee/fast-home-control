# 승인된 개발 방향과 구현

## 목적과 첫 MVP

Fast Home Control은 대화 비서가 아니라 HAOS에서 작동하는 자연어 리모컨이다. API 공급자 정보 외에 HA URL, Long-Lived Access Token, 기기 등록, 사용자 YAML을 요구하지 않는다. 첫 Dev는 실제 명령 실행이 가능한 조명·스위치 ON/OFF MVP를 배포한다. 지연을 측정하고 개선하되 1초나 특정 P95를 출시 통과 기준으로 삼지 않는다.

## Decision-1의 실제 계약

일반 chat completions/function calling을 사용하지 않는다. `state`와 이름별 `questions`를 보내고 `answers`를 받는다. `noul`은 참일 확률, `choice`는 고정 선택지와 확률 분포다. 질문은 같은 state를 독립적으로 판단하며 다른 질문의 답을 다음 질문에서 참조하지 못한다. 자유 텍스트 실행계획이나 임의 수치 매개변수를 생성하는 모델이 아니다.

OpenRouter는 `POST https://openrouter.ai/api/alpha/decisions`, Bearer 키, 모델 `microsoft/microsoft-decision-1`을 사용한다. Azure는 `POST {resource-origin}/providers/microsoft/v1/systemone`, `api-key`, 배포 이름을 사용한다. 공급자 인증·전송만 분리하며 판단·실행 코어는 공유한다. 설정된 우선 공급자의 통신/API 오류는 판단 단계에서 다른 설정 공급자로 전환할 수 있다. 잘못된 판단 응답을 더 허용적인 결과가 나올 때까지 재시도하지 않는다.

공식 자료: [OpenRouter 모델](https://openrouter.ai/microsoft/microsoft-decision-1), [Microsoft Foundry API](https://learn.microsoft.com/en-us/azure/foundry/foundry-models/how-to/use-foundry-models-microsoft-decision). 가격·성능·컨텍스트 표기는 변경될 수 있으므로 보장값으로 사용하지 않는다. 모델 확률은 한국어 가전 명령에 대해 별도로 보정된 신뢰도라고 가정하지 않는다.

## 실행 파이프라인과 후보 누락 방지

1. 서버에서 정책에 허용된 엔티티 전체를 구성한다. 숨김·비활성·진단 엔티티와 지원하지 않는 도메인만 구조적으로 제외한다. 사용자 문장의 로컬 정규식·키워드 매칭으로 기기를 제거하지 않는다.
2. 전체 허용 기기의 이름·별칭·장치 이름을 영역/공식 도메인별로 압축해 전달한다. 모델이 요청의 지원 여부와 관련 영역/도메인을 판단한다. 확실히 무관하지 않은 그룹을 넓게 유지하며 관련 그룹이 없으면 전체로 돌아간다.
3. 원문과 관련 기기의 메타데이터로 기기별 `none / turn_on / turn_off` 실행계획 후보를 판단한다. 질문마다 대상을 구조화하여 주고, 한 번에 8개 초과 시 분할한다. 첫 범위 판단과 최종 검증에는 전체 압축 카탈로그를 전달한다.
4. 요청 전체와 실행계획이 일치하는지 별도 모델 질문으로 검증한다. 초기 MVP는 단일 명령도 검증한다. 범위 판단은 0.9 이상, 중간 계획 후보는 선택 확률 0.6 이상·차순위 차이 0.2 이상, 최종 정확성 판단은 0.95 이상이어야 한다. 중간 확률만으로 실행하지 않는다. 이 값은 실험적 정책이지 보정된 사고 확률이나 정확도 보장이 아니다. 실측 평가 후 호출 통합·감축과 정책 개선을 검토한다. 작은 환경은 보통 3회, 질문이 많으면 분할 횟수만큼 증가한다.
5. 서버가 반환 타입·확률·선택지·정책·카탈로그 버전·서비스를 검증한다. 모든 대상의 최신 HA 상태를 먼저 조회한 뒤 실행한다. 상태가 이미 원하는 값이면 서비스 호출을 생략한다.
6. 실행 직전 저널에 기록하고 HA 서비스를 호출한다. 미확인 응답은 재전송하지 않는다. 다중 기기 조작은 물리적으로 원자적이지 않으므로 일부 실행과 불확실을 구분한다.

문장에 `거실불`이 등장했다는 이유로 조명을 후보에서 뺄 수 없다. `불/전등/조명`, 띄어쓰기, HA 별칭은 모델 의미 판단의 입력이다. 이름이 중복되거나 영역을 확정할 수 없으면 거부한다. 현재 요청 본문 40KB를 넘으면 전체를 자르는 대신 거부한다. 수백 개 환경에서는 전체 요약 크기·질문 수·확률 품질을 평가하고, 필요하면 모든 페이지를 검사하는 계층형 분할을 추가한다. 대규모 환경 검증 없이 무제한 지원을 주장하지 않는다.

## HA 연동과 설정

`homeassistant_api: true`로 주입되는 `SUPERVISOR_TOKEN`과 `http://supervisor/core/api`, `ws://supervisor/core/websocket`을 사용한다. 상태, 서비스, 엔티티/기기/영역 레지스트리를 읽는다. 상태·레지스트리·서비스 변경을 구독한 후 전체 스냅샷을 얻어 초기 경합을 처리한다. 이벤트와 기본 12시간 전체 재탐색을 병행하며 끊김 후 지수 backoff로 재접속한다. 재동기화 전 실행을 허용하지 않는다.

공식 앱 Configuration schema는 정적이므로 공급자·주기·보관 설정을 배치하고, 발견된 도메인에 따라 달라지는 허용 UI는 Ingress 안에서 제공한다. 첫 Dev는 light/switch만 활성화 가능하다. 나머지 도메인은 발견 사실과 미지원 상태를 표시한다. 민감 도메인은 이 MVP에서 활성화할 수 없다. 후속 센서는 읽기 전용 도구로 분리한다.

Ingress만 사용하며 호스트 포트를 공개하지 않는다. HA 공식 Ingress의 실제 프록시 peer `172.30.32.2`만 신뢰하고 전달 헤더로 인증하지 않는다. UI의 변경 요청은 별도 요청 헤더와 브라우저 origin 정보를 검사한다. 별도 외부 HTTP API는 향후 명시 인증을 갖춘 기능으로 추가한다.

## 후속 단계

1. **기술 검증 및 첫 Dev:** 두 API 계약, 한국어 동의어, 실제 HAOS 설치·서비스 호출, 모바일 UI, 실패·중복·재시작 검증. OpenRouter 실호출과 Azure 모의 계약 검증을 명확히 구분한다.
2. **기능 확장:** fan/cover/climate/media의 공식 서비스·지원 기능을 검사하는 제한된 도구 추가. 밝기·온도는 유효 범위와 단위를 서버에서 검증하고, Decision 모델의 고정 수치 선택지 방식과 별도 수치 추출 대안을 비교한다. 생성형 모델 의존을 몰래 추가하지 않는다.
3. **조건·복수 명령:** 명령 절과 상태 조건을 명시적으로 표현하고 최신 상태로 평가한다. 현재 MVP는 조건을 지원하는 척하지 않고 전체 거부한다. 계획 누락·상태 경합·부분 실행을 먼저 검증한다.
4. **품질·규모:** 다양한 한국어·영역/별칭/중복명·수백 엔티티 자료, 서비스 변경·네트워크 장애·HA 재시작, 모델 버전 회귀 평가. 호출 수와 판단/로컬 처리/HA 응답 지연을 분리한다. 처리속도는 개선 지표다.
5. **입력 브릿지:** 인증된 HTTP API, Telegram 사용자 allowlist·중복 update ID, Discord 사용자/서버 allowlist·중복 interaction ID. 설명 생성 없이 프로토콜 응답만 제공할 수 있다. 각 비밀정보는 해당 기능 사용자에게만 요구한다.
6. **안정 채널:** 사용자의 Dev 실운영 검증과 명시 승인 후 main으로 승격하고 별도 stable slug/image/version을 제공한다. 안정 버전에 Dev가 자동 유입되지 않게 한다.

범용 에이전트 플랫폼·RAG 서버·벡터 DB는 초기 범위에 포함하지 않는다. Python 비동기 백엔드와 가벼운 정적 UI, SQLite 저널, 단일 컨테이너로 운영한다.
