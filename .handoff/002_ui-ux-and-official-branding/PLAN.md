작성일: 2026-10-14 · 역할: Planner · 상태: Executor 구현 인계

## 1. 목적과 범위

사용자가 운영 반영 후 전체 기능은 정상이라고 보고했으며, 관리자 정책 편집·모델 선택·로그 열람과 모바일 리모컨의 편의성 개선을 요청했다. 기존 기능과 안전 계약을 유지하면서 사용자 모드는 간단한 리모컨으로, 관리자 모드는 관리·유지보수 중심으로 다듬는다. 이미지 생성 도구로 빠른 AI 리모컨을 나타내는 공식 아이콘을 만들고 앱·파비콘·HA 앱 스토어·GitHub 저장소의 관련 노출을 통일한다.

**이번 작업은 신규 PLAN 작성만이다.** 코드 수정, 이미지 생성, 외부 설정 변경, 커밋·배포는 이 문서 작성 단계에서 수행하지 않는다. Executor가 현재 Git과 적용되는 AGENTS.md/GEMINI.md, 이 계획을 다시 확인한 후 구현하고 같은 작업 폴더에 `REPORT.md`를 작성한다. 기존 001 이력은 보존한다. 사용자에게 특정 에이전트/모델을 전제하지 않는다.

이번 요청의 정상 동작 피드백을 Main/안정 릴리스 승인으로 해석하지 않는다. Dev 개발·검증·배포는 기존 `docs/releases.md` 절차를 따른다. 운영 HA 변경 없이 프로젝트 전용 테스트 환경에서 확인한다.

### 로그의 실제 보관·표시 계약

- 옵션 기본값은 `history_days=7`, `history_limit=1000`이며 허용 범위는 각각 1–30일, 10–10,000건이다.
- `Store.prune()`는 보관 기간을 지난 요청을 삭제한다. 건수 초과 요청은 24시간보다 오래된 항목에 적용되므로 최근 24시간 요청 ID 보호 때문에 **1,000건은 절대적인 DB 상한이 아니다.** 요청 ID 보관은 중복 실행 방지와 연결돼 있다.
- `Store.recent()`는 최근 50개를 가져오고 `/api/history`에서 hidden을 제외한다. 현재 UI는 그중 최대 8개만 보여준다.
- 다운로드 기본 요청은 `days=1`, `limit=1000`이고 API limit 최대값은 5,000이다. 저장된 전체 7일 기록과 기본 다운로드 범위를 동일하다고 설명하면 안 된다. 잘림은 기존 ZIP 메타데이터 계약을 유지한다.
- 이번에는 DB 보관·중복 실행 방지 계약을 수정하지 않는다. 표시 영역의 스크롤과 열람 안정성을 개선하고 관리자가 구분할 수 있게 짧게 안내한다.

## 3. 구현 원칙과 변경 경계

1. 기존 vanilla HTML/CSS/JavaScript와 FastAPI를 유지한다. UI 작업만을 위해 프레임워크·전역 도구·프로젝트 의존성을 새로 설치하지 않는다. 설치된 Playwright와 프로젝트 검사 명령을 활용한다.
2. 자연어 판단·실행 엔진, 지원 도메인, 정책 기본값, 후보 선정, 모델 fallback 의미를 변경하지 않는다. 제어와 조회의 독립성, Ingress 관리자 인증, Supervisor 옵션 단일 원본을 보존한다.
3. 페이지 상태와 서버 정책을 구별한다. 펼침/검색/스크롤은 UI 상태이고, 실제 허용값과 집계는 저장 성공 후 서버 응답을 기준으로 표시한다.
4. 일반 사용자 화면에는 명령 입력·실행·최근 명령·짧은 결과를 중심으로 둔다. 상시 기술 설명을 줄이되 연결 오류, 실패, 부분 실행, 실행 여부 미확정 등 행동에 필요한 정보는 유지한다. 물리 기기 완료를 확인하지 않고 완료했다고 표시하지 않는다.
5. 관리자 오류는 해당 관리자 패널에서 보이게 한다. 숨겨진 사용자 화면의 feedback에만 오류를 기록하지 않는다. 운영 키·토큰·실제 기기명/명령을 캡처·보고서·공개 자산에 포함하지 않는다.

## 4. 요청별 구현 지침과 수용 기준

### A. 관리자 제어/조회 정렬

- 엔티티 행을 `이름/영역 | 제어 | 조회`의 일정한 열로 구성한다. 이름 영역에는 `min-width: 0`와 줄바꿈을 적용하고 토글 묶음은 축소되지 않도록 한다. 캡션과 버튼을 한 그룹으로 묶어 서로 떨어지지 않게 한다.
- 도메인 헤더도 긴 이름·집계와 목록 버튼·제어·조회가 충돌하지 않게 한다. 좁은 화면에서는 이름과 조작 영역을 두 줄로 배치해도 좋지만 각 행의 제어/조회 열은 일정해야 한다.
- 스위치 시각 크기와 클릭 영역을 구별하고 터치 영역은 약 44px 이상 확보한다. ON/OFF, disabled, 저장 중, focus 상태를 명확히 한다. 접근 가능한 이름에 기기명과 제어/조회 구분을 유지한다.
- 조회 전용·미지원·보류 항목은 제어 가능처럼 보이지 않게 한다. 기존 `status`, `query_only`, `controllable` 등을 활용하고 해당 없는 열도 정렬을 유지한다. `queryable`은 현재 API에서 정책 허용 여부까지 반영하므로 단순 capability로 오해하여 OFF 상태를 다시 켜지 못하게 만들지 않는다.

수용 기준: 긴 한글/영문 이름, 영역 미지정, 여러 도메인, 조회 전용, 미지원 행에서 버튼 위치가 일정하고 모바일 가로 넘침이 없다. UI 비활성 처리를 위해 서버 정책 의미를 변경하지 않는다.

### B. 정책 편집 시 펼침·검색·위치 유지

- 도메인 키로 펼침 상태를 보관한다. 저장/재탐색/모드 왕복 때 기존 도메인의 펼침 상태를 유지하고 삭제된 도메인만 정리한다. 페이지 새로고침까지 영구 보관할 필요는 없다.
- 검색 때문에 일시적으로 펼친 상태와 사용자의 평상시 펼침 상태를 구별한다. 검색 중 결과는 보이게 하되 검색을 지우면 이전 상태를 복원한다. 펼침 버튼에 `aria-expanded`, `aria-controls`와 안정적인 대상 ID를 제공한다.
- 캐시한 도메인 데이터에서 검색을 렌더링해 입력마다 GET을 반복하지 않는 방식을 우선한다. 저장/재탐색 뒤에는 최신 데이터를 갱신한다. 동시에 발생한 갱신은 오래된 응답이 새 상태를 덮어쓰지 않게 한다.
- 정책 PUT 중 연타와 경합을 막고 완료 후 최신 허용값·집계를 표시한다. 낙관적 변경을 사용하면 실패 시 되돌린다. 오류 문구와 재시도를 해당 패널에서 제공한다.
- 전체 재렌더링을 유지하더라도 펼침·검색어·페이지/목록 스크롤·키보드 포커스를 복원한다. 안정적인 ID를 기준으로 필요한 부분만 갱신하는 구현도 가능하다.

수용 기준: 도메인 2개 이상을 펼치고 아래쪽 엔티티의 제어/조회를 연속 변경해도 목록이 접히거나 위치가 뛰지 않는다. 도메인 토글, 검색 후 편집, 재탐색, 저장 실패에서도 상태가 일관되고 실패 값을 성공처럼 남기지 않는다.

### C. OpenRouter 모델 드롭다운 + 직접 입력

- 기본 UI는 실제 선택 가능한 드롭다운으로 구성한다. 후보는 다음 두 모델과 `직접 입력`으로 제한한다. 모바일에서 후보가 확실히 노출되는 native select + 직접 입력 필드를 우선하며, datalist만으로 드롭다운 요구를 충족했다고 간주하지 않는다.

| 표시명 | 저장하는 모델 ID |
|---|---|
| Microsoft Decision-1 | `microsoft/microsoft-decision-1` |
| Jev 1.13 | `typesafe/jev-1.13` |
| 직접 입력 | 사용자가 입력한 모델 ID |

- ID는 기존 `.local/fix06-live-*` 파일명과 001 검증 이력에서 사용된 값이다. 실행 시점 공급자 변경이 의심되면 공식 모델 정보로 재확인하고 차이를 보고한다. 일반 chat 모델 호환을 보장하거나 전체 모델 목록 API를 매번 호출하지 않는다.
- 기본값 Microsoft와 기존 저장 모델을 유지한다. 기존 값이 후보에 없으면 자동으로 `직접 입력`과 해당 값으로 로드하고 다른 설정만 저장해도 값이 손실되지 않게 한다.
- 선택 후보는 기존 `openrouter_model`에 그대로 저장한다. 직접 입력의 빈 값 처리·trim·기존 기본값 규칙은 기존 계약에 맞춘다. 후보 선택과 직접 입력 전환 시 사용자가 작성 중인 값을 불필요하게 지우지 않는다.
- 후보 설명은 최소화한다. 필요하면 관리자에게만 직접 입력 모델의 Decisions API 호환 확인이 필요하다는 짧은 문구를 둔다. 비교 시험의 작은 표본을 정확도 보장으로 표시하지 않는다.

수용 기준: 두 후보 저장·재로드·재시작 유지, 임의 ID 기존 설정 로드/변경, API 키 빈 입력 유지, Azure 설정 유지가 모두 동작한다. UI 선택만으로 저장하지 않고 기존 저장 버튼으로 적용한다.

### D. 로그 내부 스크롤과 열람 안정성

- 실행 기록 목록에 뷰포트에 맞는 최대 높이와 `overflow-y: auto`를 적용한다. 높이는 대략 데스크톱 480px 이내, 모바일 50–60dvh 수준에서 실제 화면을 보고 조정한다. 로그 헤더/다운로드 조작은 목록 스크롤 밖에 둔다.
- 단일 진단 JSON도 최대 높이와 내부 스크롤을 제공하고 긴 문자열은 줄바꿈한다. 중첩 스크롤이 페이지 이동을 가두지 않게 모바일 실제 조작을 확인한다.
- 임의의 8건 잘라내기는 제거하고 현재 `/api/history` 응답 범위(최대 50개 요청 중 표시 가능한 항목)를 목록에서 열람할 수 있게 한다. 이번 작업에서는 무한 스크롤/새 페이지 API를 만들지 않는다.
- request ID로 진단 펼침 상태를 유지한다. 10초 갱신/신규 기록 추가 때 읽는 항목과 스크롤·포커스가 유지되게 한다. 변경 없는 데이터는 재렌더링을 생략하거나 필요한 부분만 갱신한다.
- 관리자에만 `최근 최대 50건`과 보관 옵션/다운로드 범위를 짧게 구별해 안내한다. 보관 옵션을 표시한다면 API에서 받은 실제 설정값을 사용한다. 기본 다운로드는 최근 1일이라는 점을 드러낸다. 기간 필터 UI 확장은 이번 필수 범위가 아니다.
- 다운로드 원문 포함 기본 OFF와 기존 익명화·비밀값 제거·잘림 메타데이터를 유지한다. 이력 삭제는 간단한 확인 절차를 두고 진행/성공/실패를 표시한다. 삭제 후 빈 상태를 갱신한다.

수용 기준: 50건 fixture 및 큰 진단 한 건에서도 영역 내부에 스크롤이 생기고 페이지 가로 넘침이 없다. 진단을 펼쳐 읽는 중 10초 이상 기다리거나 새 기록이 도착해도 접히거나 위치를 잃지 않는다. 화면 표시 범위와 다운로드·보관 범위를 혼동하지 않는다.

### E. 모바일 최근 명령 2열

- 모바일 breakpoint에서 `repeat(2, minmax(0, 1fr))`로 2열을 보장한다. 데스크톱은 현재 폭에 맞는 여러 열을 유지해도 된다.
- 버튼은 누를 수 있는 경계·배경·간격과 pressed/focus/disabled 상태를 제공한다. 명령은 가능하면 여러 줄로 읽히게 하고 긴 공백 없는 문자열도 안전하게 줄바꿈한다. 중요한 대상/동작이 말줄임만으로 가려지지 않게 한다.
- 빈 상태 문구는 그리드 전체 너비를 사용한다. 성공 명령 최대 6개, 기존 제외 규칙, 한 번 클릭 즉시 실행, busy 중 재실행 방지는 유지한다.

수용 기준: 320/360/390/430px 폭에서 명령이 2열이고 텍스트/버튼이 겹치지 않는다. 짧은 명령·긴 명령·홀수 개·빈 상태·실행 중을 확인한다. 한 번 누르면 POST가 한 번만 발생한다.

### F. 추가 UI/UX 개선

필수 범위 안에서 아래 개선을 함께 수행한다. 대규모 화면 재설계나 기능 확장은 하지 않는다.

- 사용자 모드: 상단 제목과 예시를 간결하게 다듬고 반복 설명을 줄인다. 정상 상태에서는 API/정책/진단 설명을 표시하지 않는다. 최근 명령, 실행 버튼, 진행/결과가 한눈에 보이게 한다.
- 명령 전송 실패 시 입력 문장이 사라져 재작성해야 하는 불편을 줄인다. 입력 보존/복원 시 사용자가 새로 작성한 문장을 덮어쓰지 않고, `uncertain` 결과를 자동 재전송하지 않는다.
- 관리자 모드 진입 즉시 `loadStatus()`를 포함해 연결 상태를 갱신한다. 설정 저장·재탐색·다운로드·정책 저장의 busy 상태와 실패를 해당 위치에 표시한다. 폴링으로 작성 중인 설정을 덮어쓰지 않는다.
- 모바일 관리자 패널 헤더/로그 액션을 줄바꿈하고 검색 필드 스타일을 다른 입력과 맞춘다. 키 삭제 체크박스·상태 배지·공급자 탭의 충돌을 해소한다.
- 키보드 탐색, 눈에 보이는 focus, 입력 label, 결과/오류 `role=status` 또는 적절한 live region, 터치 영역을 확인한다. 컬러만으로 상태를 구분하지 않는다.

Executor는 추가로 발견한 문제와 반영 여부를 REPORT에 기록한다. 사용자 화면에 설명·배너·설정·새 메뉴를 쌓는 개선은 피한다.

### G. 이미지 생성 기반 공식 아이콘과 노출 통일

**이미지 생성 도구를 실제로 사용한다.** 당시 사용 가능한 이미지 생성 skill/도구 지침을 확인하여 실행하고 도구·프롬프트·원본·파생 과정을 기록한다. 단순 문자 이모지, 외부 서비스 로고 복사, 수작업 SVG만으로 대체하지 않는다.

- 방향: Fast Home Control의 빠른 AI 리모컨. 간결한 리모컨 실루엣에 번개/전진/즉각 반응을 표현하는 요소를 결합한다. AI는 과한 회로·로봇 묘사보다 작은 포인트로 표현한다. 현재 녹색 accent와 조화시키되 작은 크기에서도 명확하게 한다.
- 글자 없이 16/32px에서 인식 가능한 단순 형태, 선명한 대비, 정사각 구도/안전 여백을 우선한다. 빛 번짐·많은 버튼·미세 패턴·복잡한 속도선을 피한다. 같은 디자인을 원본으로 모든 크기를 파생한다. 워드마크가 필요하면 기존 제품명을 별도로 배치한다.
- 산출물 예시: `docs/branding/`에 생성 원본 및 짧은 사용 지침, `static/`에 32/192/512px PNG, favicon ICO(16/32/48), Apple touch 180px, 필요 시 header용 자산. 정확한 파일명은 Executor가 정하되 아래 노출 매핑과 단일 원본을 문서화한다. 없는 벡터 원본을 있다고 기록하지 않는다.
- 투명 배경이 필요한 앱/헤더용과 바탕색이 필요한 소셜 카드용을 구별한다. 변환은 허용된 도구와 설치된 라이브러리를 사용하고 생성·편집 도구의 제약을 따른다. 사용하지 않는 PWA manifest/service worker를 이번에 추가하지 않는다.

| 노출 위치 | 작업 및 검증 |
|---|---|
| 웹 UI 헤더 | 공식 mark와 제품명 적용. 좁은 화면에서도 모드 버튼/연결 경고가 충돌하지 않게 한다. 장식 이미지에는 중복 낭독을 피한다. |
| 브라우저 탭/모바일 북마크 | favicon 및 apple-touch-icon 링크 추가. Ingress prefix 아래 상대 URL로 실제 200/MIME/이미지를 확인한다. 호스트 루트 `/static/...` 가정을 피한다. |
| HA 앱 스토어/앱 상세 | `addon/icon.png`, 필요하면 `addon/logo.png`에 같은 디자인을 적용한다. 실제 지원 규격·파일 위치는 구현 시 HA 공식 문서와 테스트 Supervisor에서 확인한다. |
| HA sidebar | 현 `panel_icon: mdi:remote`는 아이콘 식별자다. PNG 경로를 임의로 넣지 않는다. 공식 사용자 이미지 지원 여부를 확인하고 가능하면 동일 mark 적용, 불가하면 가장 맞는 지원 MDI를 유지하고 플랫폼 제한을 REPORT에 기록한다. |
| GitHub README/앱 DOCS | 동일 공식 mark를 사용한다. Dev의 실제 렌더링·이미지 링크를 확인하고 독립적인 다른 아이콘을 도입하지 않는다. |
| GitHub social preview | 같은 mark로 저장소 공유 카드(예: 1280×640)를 만들고 저장소 Social preview에 적용 가능한 수단/권한을 확인한다. 파일 커밋만으로 저장소 설정이 바뀌었다고 보고하지 않는다. 지원 API/도구가 없으면 업로드할 최종 파일과 정확한 설정 경로를 제공하고 해당 항목을 외부 수동 조치로 명시한다. |

GitHub의 사이트 favicon이나 개인/조직 공용 avatar는 프로젝트 자산과 별개다. 사용자 요청을 개인/조직 전체 이미지 변경으로 확대하지 않는다. README/Social preview/HA 앱 자산 등 이 저장소가 제어하는 접점을 통일하고 플랫폼 고정 아이콘의 한계를 명확히 한다. Main은 별도 승인 없이 수정하지 않는다.

수용 기준: 생성 원본과 도구 사용 기록이 있고 모든 프로젝트 아이콘이 같은 디자인이다. 작은 favicon·밝고 어두운 배경·모바일 header·HA 앱 목록에서 판독 가능하다. 공개 노출 적용 완료와 파일만 준비된 항목을 구분한다.

## 6. 검증 계획

### 자동 검사

기존 환경과 lock을 사용해 다음을 수행한다. 설치/동기화가 필요하면 저장소의 기존 `uv` 절차를 따른다.

```sh
uv run ruff check addon/app tests scripts
uv run ruff format --check addon/app tests scripts
uv run pytest -q
node --check addon/app/fhc/static/app.js
git diff --check
```

CI의 requirements 일치·amd64/arm64 빌드 검사도 Dev 배포 시 통과해야 한다. 버전을 올리면 앱 VERSION, `addon/config.yaml`, `pyproject.toml`, HTML fallback, changelog의 일치를 확인한다. 다음 Dev 번호는 실행 시 확인하며 현재 기준 다음 후보는 `0.2.0-dev.10`이다.

### 브라우저 동작 검증

수정 전후 데스크톱(예: 1280px)과 모바일 320/360/390/430px를 확인한다. 스크린샷과 DOM/요청 관찰을 결합한다. 단순 CSS 문자열 검사로 동작 검증을 대체하지 않는다. 현재 설치된 Playwright를 활용하며, API fixture와 실제 Ingress 결과를 구별한다.

1. 여러 도메인 펼침 → 아래쪽 제어/조회 저장 → 검색 후 저장/검색 해제 → 재탐색 → 모드 왕복. 펼침·위치·포커스·집계 확인.
2. 정책 PUT 실패/지연, 빠른 연속 조작, 검색 중 갱신으로 응답 역전/중복 PUT/조용한 오류가 없는지 확인.
3. Microsoft/Jev/직접 입력 저장·재로드, 후보 밖 기존 값, 다른 설정만 저장, 키 빈 입력 유지, API 실패 확인. UI 회귀를 위해 유료 실제 모델 호출을 반복할 필요는 없다.
4. 50건 및 큰 JSON/긴 문자열 fixture, 진단 펼침 후 10초 갱신, 새 항목 추가, 로그 내부 스크롤과 다운로드/삭제 확인.
5. 모바일 최근 명령의 열 수·동일한 열 폭·긴 문장 가독성·빈 상태·busy를 확인하고 연타 시 POST 1회를 확인.
6. 정상/연결 끊김/미설정/실패/부분 실행/uncertain의 사용자 피드백, 전송 실패 입력 보존, 키보드 조작, 200% 확대와 페이지 가로 넘침 확인.
7. 헤더/파비콘/Apple 아이콘/README/HA 앱 자산/공유 카드의 일관성, HTTP 200·MIME·Ingress 상대 경로, 브라우저 콘솔 오류 확인.

### 설치·배포 검증

Dev를 배포한다면 기존 프로젝트 전용 HAOS에 공식 저장소 업데이트로 설치·기동하고 Ingress에서 정책 저장·모델 옵션 유지·아이콘 경로·모바일 화면·진단 다운로드를 확인한다. 운영 HA나 물리 기기에서 시험하지 않는다. 필요한 명령 실행 확인은 가상 기기로 제한하고 유료 모델 호출을 최소화한다.

`docs/releases.md`의 설치 검증 → 검증된 소스 commit의 Dev tag/prerelease 순서를 지킨다. 테스트 VM/임시 서버를 켰다면 종료·정리와 자원 상태 갱신을 기록한다. 수행하지 못한 설치·외부 노출 검증은 공백으로 보고하며 mock 결과를 실제 설치 성공으로 표기하지 않는다.

## 7. 완료 기준 및 REPORT 인계

완료 기준은 요청 1–7에 대해 구현·검증 결과와 제한을 한 항목씩 대조할 수 있는 것이다. 특히 다음을 충족해야 한다.

- 제어/조회 정렬, 정책 편집 후 펼침 보존, Microsoft/Jev 선택과 직접 입력이 실제 브라우저에서 동작한다.
- 로그 목록·긴 진단에 내부 스크롤이 생기고 자동 갱신이 읽는 상태를 잃게 하지 않는다. 보관/표시/다운로드 범위가 정확하다.
- 모바일 최근 명령은 2열이고 사용자 모드는 설명을 최소화하며 기존 실행 안전성/결과 의미를 유지한다.
